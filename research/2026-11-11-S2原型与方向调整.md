# S2 原型与方向调整：数学暂停，转产品/功能/方案

- 日期：2026-11-11
- 原型：pipeline/runs/experiments/math-s2-prototype.mp4
- 源码：pipeline/experiments/math-s2-prototype
- 状态：**数学竖线暂停；产品/软件/功能/方案为后续主线**

## 1. S2 原型是什么

- 14.7s / 439 帧 / 1920×1080 / 30fps / -16.0 LUFS
- 内容：温度计 -1/-3 → 抽出水平数轴 → 0/-1/-3 落点 → “左=小” → -3 < -1
- 目的：验证“一个视觉锚点 + 变化过程 + 观众预测”是否比卡片讲解更清楚
- 不是完整课，也不是教材顺序中的一课

## 2. 原型自检

| 项 | 结果 |
|---|---|
| 视觉锚点 | 温度计 → 数轴，基本连续 |
| 观众动作 | 开场有“哪个温度更低”的预测 |
| 画面独立解释 | 不看旁白也能看出 -3 在 -1 左边 |
| 问题 | 温度计到数轴的过渡仍像“切换”，不是真正的同构变形；旁白偏快；14.7s 太短，预测停顿不够 |
| 结论 | 视觉语法方向成立，但需要 25–30s 和更顺的变形；**不再在数学上继续投入** |

## 3. 为什么数学暂停

用户指出：当前讲解顺序与中国中学教案不一致。  
这是对的：教材有固定单元顺序（正负数 → 数轴 → 相反数/绝对值 → 大小比较 → 运算），不是“一个视觉点子”就能成一课。

数学教学需要：

- 对齐课标/教材/教案顺序；
- 知道学生先备知识与常见误区；
- 有练习、反馈、迁移；
- 有真实教师/学生验证。

这不是我们当前的主场。继续做数学，会陷入“视觉上更好看，但教学上不成立”。

## 4. 转向：产品 / 软件 / 功能 / 方案

这三类更符合我们的场景，因为：

- 画面有真实对象：界面、按钮、数据、流程、前后状态；
- 讲解顺序由“用户任务”决定，不依赖教材；
- 视觉可以承担因果：操作 → 状态变化 → 结果；
- 我们已有 WorkBuddy vs Qoder 的内容资产和产品理解；
- B2B/产品团队更愿意为“讲清楚功能/方案”付费。

## 5. 三条内容线

### A. 产品介绍（30–60s）

- 给谁：潜在客户/新用户
- 结构：谁的问题 → 产品是什么 → 关键能力 → 结果 → CTA
- 视觉：产品界面/真实操作占主角，不做纯卡片

### B. 功能讲解（30–60s）

- 给谁：已有用户/销售/客户成功
- 结构：旧做法 → 新操作 → 状态变化 → 结果
- 视觉：真实 UI/录屏 + 局部放大 + before/after
- 这是最适合 MG 的类型：光标、点击、面板展开、数据更新、流程连线

### C. 方案介绍（60–90s）

- 给谁：企业客户/决策者
- 结构：场景痛点 → 方案架构 → 关键机制 → 客户结果 → 证明
- 视觉：抽象架构图、数据流、角色/系统关系；代码绘制即可

## 6. 新的场景契约（产品向）

每个 Scene 必须先写：

1. 用户任务是什么？
2. 画面里的“真实对象”是什么（UI/数据/流程）？
3. 它发生了什么状态变化？
4. 观众要做什么判断？
5. 证据是什么（结果/指标/客户原话）？

禁止：

- 用卡片代替产品界面；
- 用旁白解释画面已经能说明的东西；
- 为了 MG 加与任务无关的动效；
- 一个版式撑 30 秒以上。

## 7. 下一步

1. 选一个具体功能做 45s 蓝图：建议从 WorkBuddy 的文档/表格/会议能力里选一个；
2. 需要真实 UI 截图/录屏素材；没有素材就先做“抽象 UI 示意”，但标注非真实；
3. 先写 4 个 Scene：痛点 → 操作 → 状态变化 → 结果；
4. 纸面确认后，再做 20s 单场景原型；
5. 数学 S2 原型只作为“视觉语法参考”，不进入产品片。

## 8. 结论

- **数学竖线：暂停，不再投入。**
- **产品/软件/功能/方案：继续，作为主线。**
- 保留 Remotion/TTS/字幕/QC；保留“视觉锚点/状态变化/预测”的方法；
- 不再用“卡片 + 旁白”做产品讲解，优先真实界面与状态变化。
