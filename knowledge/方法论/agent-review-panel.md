# Agent 脚本评审团 · 无业务老师时的对抗式评审

## 一句话定位

没有业务老师、业务方也说不清要什么时，用 **3 个独立、对抗式 Agent**（学科/学习科学/新手）做评审，Lead 负责**证据裁决**：只接受能引原文、能说清机制、能给出改法的意见；好坏由 Lead 判断，不由「看起来专业」决定。

## 适用场景

- 没有外部学科专家（SME），或 SME 成本高/排期长。
- 业务方只给主题，不给明确验收标准。
- 脚本、分镜、课程、产品讲解等需要「内容站得住」的项目。
- 不适用：需要真实教学实验数据、临床/法律/安全等高风险结论（仍需人类专家）。

## 原理与判断标准

1. **独立性**：评审 Agent 不参与写作，彼此看不到对方意见，避免互相锚定。
2. **对抗性**：默认不信任作者；只认原文引用、机制解释、可执行改法；禁止客套。
3. **多视角**：学科（对不对）、学习科学（学不学得会）、新手（听不听得懂）三个视角缺一不可。
4. **证据裁决**：Lead 不按「谁说得凶」裁决，按「引文是否准确、机制是否成立、改法是否可执行」裁决；事实错误优先于教学偏好。
5. **可复现**：评审写文件、带行号/引文、给分级（P0/P1/P2）；Lead 记录接受/拒绝理由。
6. **不是万能**：Agent 会共享盲区；高风险或高成本项目仍需真实用户试播/人类专家抽检。

## 角色与提示词

### 角色 1 · 学科评审（SME Critic）

查：定义、事实、课标/教材顺序、超纲、例子是否成立、测评是否对齐。
输出：评分 1–5；P0/P1/P2；最危险 3 个问题；verdict。

### 角色 2 · 学习科学评审（Pedagogy Critic）

查：目标可测、证据是否只考再认、认知负荷、Mayer 原则、误区处理、迁移、前测/后测。
输出：评分 1–5；P0/P1/P2；最危险 3 个设计问题；verdict。

### 角色 3 · 新手评审（Novice Critic）

以目标受众第一人称：哪里听不懂、哪里无聊、哪里会记错、后测题体感、一句话复述、最该改 3 处。
输出：不要求理论术语，只要求具体。

### 可选角色 4 · 制作评审（Production Critic）

查：时长与旁白量、画面可实现性、版权/素材、字幕/版式冲突。

### 提示词硬规则

- 只评审，不改脚本；
- 每条意见必须引原文（带行号/原文片段）；
- 每条必须写「为什么错 + 怎么改」；
- 分 P0（必须改）/ P1（不改会浪费试播）/ P2（可选）；
- 必须给 1–5 分与 verdict（pass / revise / reject）；
- 禁止「整体不错」「建议优化」这类空话；
- 独立写文件，不参考其他评审。

## 可操作步骤

1. **锁定评审对象**：给 Agent 脚本路径、SOP、来源；明确只读范围。
2. **并行派 3 个 Agent**：学科/学习科学/新手；各自写独立文件（如 research/reviews/日期-角色.md）。
3. **Lead 通读**：先核对引文是否真的在原文；再看机制是否成立；最后看改法是否可执行。
4. **分级合并**：同一问题跨评审出现→升级；互相冲突→按规则裁决。
5. **裁决记录**：接受/部分接受/拒绝 + 理由；保留反对意见。
6. **改稿**：只改被接受项；P0 必须清零；P1 要么改要么写豁免理由。
7. **二轮评审**：改完再派一轮（可同角色/新角色），确认 P0 已消；未过不进制作。
8. **必要时人工抽检**：高风险内容找人类专家；低成本项目至少 5 人试播。

## 裁决规则（Lead 用）

| 冲突 | 裁决 |
|---|---|
| 学科事实 vs 教学偏好 | 事实优先；事实错一票否决 |
| 学科「太浅」vs 学习科学「太难」 | 看先备知识与课标；以「最近发展区」为准，必要时拆两层 |
| 教学理论 vs 新手体验 | 先修新手卡点；理论用来解释/约束，不用来压体验 |
| 两个评审都指出同一问题 | 升级为 P0/P1，优先改 |
| 评审意见无法引原文 | 降级/拒绝，要求补证据 |
| 改法成本过高 | 保留问题，写豁免理由与替代方案，不假装已解决 |
| 评审互相矛盾且都有理 | 缩小范围/拆镜头，避免二选一硬碰 |

## 参数与阈值

| 项 | 推荐 |
|---|---|
| 评审人数 | 3（学科/学习科学/新手） |
| 独立写文件 | 每人 1 份，不互看 |
| P0 清零 | 必须 |
| P1 处理 | 改或书面豁免 |
| 评分 | 1–5；任一维度 ≤2 视为不通过 |
| verdict | pass / revise / reject |
| 二轮 | 改稿后必须 |
| 高风险 | 人类专家抽检 |

## 常见反例

| 反例 | 问题 | 改法 |
|---|---|---|
| 只派一个「万能评审」 | 视角单一，容易漏 | 至少 3 个角色 |
| 评审互相看稿 | 锚定、趋同 | 独立文件、并行 |
| 只收「不错/建议优化」 | 不可执行 | 强制引文 + 改法 + 分级 |
| Lead 按语气裁决 | 谁凶听谁 | 按证据/机制/可执行性 |
| 改完不复审 | P0 可能没消 | 二轮评审 |
| 把 Agent 评审当「已验证」 | 没有真实用户数据 | 只称「评审通过」，试播后再说验证 |

## 验证方式

- 每份评审是否有原文引用、P0/P1/P2、verdict。
- Lead 裁决表是否覆盖所有 P0，接受/拒绝都有理由。
- 二轮评审 P0 是否为 0。
- 改稿后目标/证据/脚本是否一致。
- 有条件的项目：5–10 人试播，后测数据。
