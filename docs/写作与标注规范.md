# 写作与标注规范

> 本文件定义**所有条目的 frontmatter 字段、正文结构、事实标注与来源写法**。校验脚本按此实现，Lead 按此验收。

---

## 1. Frontmatter 是机器的接口

每条知识 / SOP 必须以下列 frontmatter 开头（`---` 包裹）。**字段名、大小写、取值必须与下表一致**；校验脚本会查。

### 1.1 知识条目（`knowledge/**`，不含 README）

| 字段 | 必填 | 取值 / 说明 |
|---|---|---|
| `id` | 是 | `kb/<slug>`，与文件名一致，全局唯一 |
| `title` | 是 | 中文标题，「对象 · 定位」 |
| `type` | 是 | `库` / `工具` / `方法论` / `工作流` / `环境` |
| `domain` | 是 | 制作环节，inline list，如 `[转码, 剪辑, 自动化]` |
| `status` | 是 | `草稿` / `可用` / `已验证` / `归档` |
| `confidence` | 是 | `高` / `中` / `低`（对内容整体判断） |
| `license` | 库/工具 是 | SPDX 或通行写法；多许可证写清适用部分 |
| `repo` | 库/工具 是 | 源码仓库 URL；无仓库给官网 |
| `docs` | 库/工具 是 | 官方文档 URL |
| `language` | 库/工具 是 | 主语言，如 `C`、`Python`、`TypeScript` |
| `platform` | 库/工具 是 | inline list：`macOS` / `Linux` / `Windows` / `浏览器` / `云端` |
| `tags` | 是 | inline list，3–8 个，用于检索 |
| `related` | 是 | 关联条目 id 列表，可为 `[]` |
| `updated` | 是 | `YYYY-MM-DD` |
| `owner` | 是 | 写作 Agent 名（Lead / lib-scout / …） |

### 1.2 SOP（`sop/*.md`，不含 README / 模板）

| 字段 | 必填 | 取值 / 说明 |
|---|---|---|
| `id` | 是 | `sop/<slug>`，与文件名一致 |
| `title` | 是 | 中文标题 |
| `type` | 是 | 固定 `sop` |
| `video_type` | 是 | 视频形态，如「口播知识」「混剪卡点」 |
| `duration` | 是 | 成片时长区间，如 `"30–180s"`（含引号） |
| `aspect` | 是 | 主画幅，如 `"9:16"` |
| `platforms` | 是 | inline list，主发平台 |
| `difficulty` | 是 | `低` / `中` / `高` |
| `tools` | 是 | inline list，主用工具链 |
| `status` | 是 | 同上四态 |
| `updated` | 是 | `YYYY-MM-DD` |
| `owner` | 是 | 写作 Agent 名 |

### 1.3 技能（`skills/<name>/SKILL.md`）

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 与目录名一致，小写 kebab-case |
| `description` | 是 | 写**何时触发**：做什么 + 触发条件，Agent 靠它决定是否加载 |
| `version` | 是 | 语义化版本，如 `0.1.0` |

## 2. 正文结构（必备节）

### 2.1 知识条目 · 库 / 工具

```text
## 一句话定位
## 能解决什么 / 不解决什么
## 核心能力
## 安装 / 获取
## 最小可用示例
## 优缺点与坑位
## 适用 / 不适用
## 与本仓 SOP / 其他条目的关系
## 实测记录
## 来源
```

### 2.2 知识条目 · 方法论 / 工作流 / 环境

```text
## 一句话定位
## 适用场景
## 原理与判断标准
## 可操作步骤
## 参数与阈值
## 常见反例
## 验证方式
## 关联条目
## 来源
```

### 2.3 SOP

```text
## 适用 / 不适用
## 交付规格
## 前置准备
## 流程总览（阶段 × 产出 × 时间预算）
## 分阶段操作
## 参数速查
## 质量门禁（QC）
## 常见问题
## 可自动化环节
## 变体（平台 / 时长 / 素材条件）
## 复盘与改进
## 关联条目
```

允许加节；必备节不可缺。

## 3. 事实标注

| 标记 | 用法 | 例 |
|---|---|---|
| `[事实]` | 可验证的客观信息 | `[事实] FFmpeg 采用 LGPL/GPL 双许可（见来源 1）。` |
| `[实测]` | 本机跑过 | `[实测] 2026-11-03，ffmpeg 9.0.2，8 核 M 系列，60s 1080p H.264 转码 ≈ 8s。` |
| `[推断]` | 经验推理 | `[推断] 4K 代理会显著改善 8GB 内存机器的拖拽体验（依据：码率与解码压力关系）。` |
| `[待确认]` | 信息缺失 | `[待确认] 该库 v2 是否仍支持 Node 18，需查 release notes。` |

规则：

1. **数字必须有出处**：版本、价格、性能、平台阈值（码率 / 分辨率 / 时长限制）一律带来源或 `[实测]`。
2. 同一段里先给结论，再给依据；不要“据说 / 可能 / 大概”。
3. 价格、政策、算法规则类信息，写「截至 YYYY-MM-DD」。

## 4. 来源写法

统一放文末 `## 来源`，编号列表：

```markdown
## 来源
1. [FFmpeg 官网](https://ffmpeg.org/)（访问 2026-11-03）
2. [FFmpeg License](https://ffmpeg.org/legal.html)（访问 2026-11-03）
3. 本机实测：`ffmpeg -version` → 9.0.2（2026-11-03）
```

规则：

- 外部来源：标题 + 链接 + 访问日期。
- 实测：写命令与结果摘要。
- 内部引用：用相对链接指向本仓条目，不重复抄内容。

---

## 5. 语言与排版

1. 中文为主，短句；一段一个意思。
2. 术语首次出现中英对照：代理剪辑（proxy editing）、时间线（timeline）。
3. 命令统一用 ```bash` 代码块；参数解释用表格或列表。
4. 表格优先于长段落；步骤用有序列表。
5. 不用 emoji 当标题；除本规范要求的标记外不加装饰。
6. 标题层级最多到 `###`，避免层级过深。

---

## 6. 状态流转

| 从 | 到 | 条件 |
|---|---|---|
| 草稿 | 可用 | frontmatter 完整 + 必备节齐全 + 有来源 + 至少 1 个可执行示例 |
| 可用 | 已验证 | 有 `[实测]` 记录且可复现（命令 / 工程 / 结果） |
| 任意 | 归档 | 被替代 / 不再维护；顶部写替代方案 |

**不允许**：无实测标「已验证」；无来源标「[事实]」。

---

## 7. 更新规则

1. 改动内容 → 更新 `updated`。
2. 大改（结构 / 结论反转）→ 在条目顶部加「变更记录」小节，写日期 + 改了什么 + 为什么。
3. 删除信息前确认没有其他条目引用（`grep` 一下 id）。

## 8. 自检清单（写完逐条过）

- [ ] frontmatter 字段齐全、取值合法、id 与文件名一致

- [ ] 仓内链接能点开
